A. Project overview

A.1 Purpose

The AI-Based Exam Proctoring System provides a controlled environment for university exams: identity verification, AI proctoring, randomized exams, automated grading where possible, AI question generation, integrity scores and collusion reports. Actors are Instructor, Student, Administrator and the AI proctoring module.

B.3 Main user flows

  1. First sign-in of a new instructor: an admin created the account (via the Flutter app or POST /api/admin/instructors) and gave the instructor a temporary password → sign in → forced change-password page → exam list.
  2. Prepare an exam: New exam → details page → add questions → Publish (server validates the whole exam) → status Published.
  3. Change before the start: edit details or questions of a Draft or Published exam while it has not started; unpublish to return to Draft; or cancel (irreversible).
  4. After the start time: the exam and its questions are read-only; a Draft can still be deleted.
  5. Student sign-up: Sign up → 201 → success panel ("account created; student exam features are not available yet") with a link to sign in. Signing in works, but a Student has no pages in this app yet (§2.4 is open).

C. Complete backend API reference

C.1 Conventions (all endpoints)

  • Base path /api. JSON bodies, camelCase property names. Enums are sent and returned as strings ("Draft", "Mcq"). GUIDs are strings. Times are ISO 8601 strings; responses always use UTC (+00:00).
  • Protected endpoints need Authorization: Bearer <accessToken>. Every protected endpoint also enforces: active account, unchanged security stamp, and the forced password change (except where noted).
  • Errors: ProblemDetails with status, detail, a machine-readable code and, for validation errors, errors (field → messages). ASP.NET Core also adds type, title and usually traceId; don't rely on those.
  • A role failure (e.g. a Student calling an instructor endpoint) is 403 without a code. A missing/invalid/expired token is 401 with code: "token_invalid" and header WWW-Authenticate: Bearer.
  • Unknown ids, malformed ids and other instructors' data all answer 404 (existence is never revealed).
  • Create endpoints return 201 with the body and no Location header.

C.3 Authentication endpoints

POST /api/auth/login

Request LoginRequest: { "email": string, "password": string }. Body limit 16 KB. Validation: "Email is required.", "Password is required."

// 200 TokenResponse
{
  "tokenType": "Bearer",
  "accessToken": "<JWT>",
  "accessTokenExpiresAt": "2026-10-23T09:15:00+00:00",
  "refreshToken": "<opaque token>",
  "refreshTokenExpiresAt": "2026-10-30T09:00:00+00:00",
  "mustChangePassword": false,
  "user": { "id": "<guid>", "fullName": "Dr. Example", "email": "instructor@example.edu", "role": "Instructor" }
}

Errors: 400 validation_failed; 401 invalid_credentials ("The email or password is incorrect."); 401 account_locked (after 5 failed attempts, 15 minutes); 403 account_deactivated; 403 temporary_password_expired ("The temporary password has expired. Ask an administrator for a new one."); 413 body too large; 429 rate limit. Role values: Admin, Instructor, Student.

POST /api/auth/refresh

Request { "refreshToken": string }. 200 → a new TokenResponse (new access and refresh token; the old refresh token is used up). Errors: 400 validation_failed; 401 token_invalid ("The refresh token is invalid or has expired."); 401 refresh_token_reused (an already-rotated token was presented: the whole session family is revoked); 403 account_deactivated/temporary_password_expired; 429.

POST /api/auth/logout

Bearer token required. Request { "refreshToken": string }. 204 (ends that session's token family; the current access token stays valid until it expires). Errors: 400, 401.

POST /api/auth/change-password

Bearer token required (allowed during a pending change). Request { "currentPassword": string, "newPassword": string } (no confirmation field). 200 → new TokenResponse; every earlier session and access token of the account stops working. Errors: 400 validation_failed with field messages, e.g. currentPassword: "The current password is incorrect.", newPassword: "The new password must be different from the current password." or Identity policy messages; 401 account_locked after too many wrong current passwords; 401 token_invalid.

Password policy (Identity): at least 8 characters, an uppercase letter, a lowercase letter and a digit; no symbol required.

GET /api/auth/me

200 { "id", "fullName", "email", "role", "mustChangePassword" }. 401 token_invalid.

POST /api/auth/register (student sign-up – in React scope)

Source: AuthController.Register, RegisterStudentRequest, RegisterStudentRequestValidator, AccountFieldRules, EmailRules, AuthService.RegisterStudentAsync. Anonymous; rate limit 5 per minute per IP. No body-size attribute (the 16 KB limit applies only to login, refresh, logout and change-password).

// Request RegisterStudentRequest – exactly these four fields
{ "fullName": "Sara Ahmed", "email": "sara@example.edu", "password": "Example1pass", "confirmPassword": "Example1pass" }

// 201 RegisterStudentResponse – no tokens; the user is NOT signed in
{ "id": "<guid>", "fullName": "Sara Ahmed", "email": "sara@example.edu", "role": "Student" }
Field (error key)Server rule and exact message
fullNameRequired after trimming: "Full name is required."; at most 150 characters after trimming: "Full name must be at most 150 characters."; no control characters: "Full name must not contain control characters.". No other format rule; Arabic names are valid.
emailRequired: "Email is required."; otherwise "Email is not a valid email address." unless, after trimming: 1–256 characters, no whitespace, control or invisible format (Unicode Cf) characters, exactly one @ with text on both sides, and a domain that contains a dot, does not start or end with . or - and contains no ... Any email domain; non-English letters allowed.
passwordRequired: "Password is required."; then the Identity policy (at least 8 characters, an uppercase letter, a lowercase letter, a digit) with Identity's own messages.
confirmPasswordMust equal password: "Passwords do not match." Validated, never stored.

Other responses: 409 duplicate_account ("An account with this email already exists."; also for deactivated accounts and any role); 429 rate limit. Extra JSON properties (for example role or universityId) are ignored; the role is always Student and the account is Active immediately (no email verification).

University identification is not a blocker. The Revision 3.3 open decision on identifying a student's university was withdrawn in Revision 3.4 (D11, D12): any university and any email domain are accepted, accounts store no university data, and the sign-up form has exactly the four fields above. §2.5 keeps "university affiliation" only as a future question that "is not a registration requirement" and would never be added to the sign-up form. Do not add a university field, dropdown or ID.

D. Business logic and UI behaviour

D.1 Exam creation and editing

  • Fields: title, description, start date/time, duration. Never show inputs for status, warning limit, published time or owner.
  • Start time must be in the future (server clock). On edit, the check applies only if the start time is changed; send the original startsAt string back unchanged if the user did not touch the field (avoids minute-rounding being treated as a change).
  • Edit is possible only while status is Draft or Published and phase is Upcoming. Hide or disable "Edit" otherwise and explain why. The server is authoritative: if the exam starts while the page is open, PUT returns 409 → show detail and reload the exam.
  • Concurrent edits: the later save wins (no version field). RECOMMENDATION reload after saving.

D.2 Time zone handling

  • Input: the instructor enters local wall-clock time (<input type="datetime-local">). Send it with the browser's offset, e.g. 2026-11-01T09:00:00+03:00, or as UTC Z via Date.toISOString(). Both are valid. Never send a value without an offset (rejected) and never treat local time as UTC.
  • Output: the server always returns UTC (+00:00). Display in local time and state the time zone near date fields.
  • phase is computed by the server when the exam is read; it can become stale while a page stays open.

D.3 Duration

Whole minutes, 1–360 (6 hours). endsAt is computed by the server.

Publish refusal messages (first blocking problem, questions in position order): "The exam has no questions.", "Question N has no text.", "Question N has more than 4000 characters of text.", "Question N has invalid marks.", "Question N has a model answer longer than 4000 characters.", "Question N is an essay question and must not have options.", "Question N has an option without text.", "Question N has an option longer than 1000 characters.", "Question N needs at least 2 options.", "Question N has more options than the current maximum of M.", "Question N needs exactly one correct option.", "Question N repeats an option text.". In practice, for API-created questions only the first, the start-time message and the maximum-options message can occur.

UI rules: show Publish only for Draft; Unpublish and Cancel only for Published; Delete only for Draft; disable lifecycle buttons when phase is not Upcoming (Delete stays available for a Draft). Every action opens a confirmation dialog; Cancel and Delete are marked irreversible. On success, replace the displayed exam with the 200 response. On 409/404, show detail (or the friendly 404 text) and reload the exam. Never change the status locally without a server response.

Known backend limitation: under a narrow race (another request changes the status at the same moment) a refusal's detail can read "The start time has passed." although the real reason was the status. The 409 itself is correct.

D.5 Questions

  • Whole-question writes: the form sends the full question including all options; a PUT replaces everything.
  • Positions are server-assigned (append; renumber after delete). There is no reordering; don't offer drag-and-drop.
  • MCQ: at least 2 options; exactly one correct (use radio buttons); option texts must be distinct (trimmed, case-insensitive); the maximum count is a server setting (default 8) that is not exposed by the API – don't hard-block at 8; show the server's 400 message if exceeded. If the maximum was lowered, existing over-limit questions stay stored; editing another question still works; publishing reports the over-limit question.
  • Essay: no options (send []); hide option controls.
  • Marks: number > 0, ≤ 9999.99, at most 2 decimals; display with 2 decimals.
  • Model answer: optional; visible to the instructor only (students never receive it).
  • Writes allowed only while the exam is Draft/Published and Upcoming. Questions can always be read.
  • Deleting the only question of a Published exam is refused (409); explain it in the delete dialog.

D.6 Validation errors

Map errors keys to fields: sign-up keys fullName, email, password, confirmPassword; exam keys title, description, startsAt, durationMinutes; question keys type, text, marks, modelAnswer, options (group), options[i].text / options[i] (the i-th option in the order sent, 0-based); auth keys email, password, currentPassword, newPassword. Show detail above the form. Malformed-JSON errors use framework key names – show the general message.

D.7 Pagination, sorting, filters

Exams: page/pageSize (1–100, default 10) and status only. No search, no custom sort (newest start first is fixed). Questions: no paging. RECOMMENDATION keep filter and page in the URL query string.

D.8 Ownership and access denied

Instructors only see their own exams. Another instructor's exam id gives 404 – show "not found or not yours". Admin and Student accounts get 403 without a code on all exam endpoints – show an "instructor access only" screen.

D.9 Temporary password flow

Admin-created instructors receive a temporary password (default lifetime 72 hours, Auth:TemporaryPasswordHours). Login returns mustChangePassword: true; route the user to the change-password page; all other endpoints answer 403 password_change_required until changed. An expired temporary password → 403 temporary_password_expired at login: tell the user to ask an administrator.

D.10 Student sign-up (owner decision: included)

  • Form fields exactly as C.3: full name, email, password, confirm password. No role, university or any other field.
  • Client checks mirror the server (required fields, 150-character name, basic email shape, password policy, confirmation matches); the server stays authoritative and its errors are mapped to the four fields (password may carry several Identity policy messages).
  • On 201: clear the form (including both passwords) and show a success panel: "Your student account has been created. Student exam features are not available in this app yet." with a "Sign in" link. Do not sign in automatically and do not store anything from the response.
  • On 409 duplicate_account: show the message on the email field. On 429: "Too many attempts, wait a minute".
  • A Student who signs in gets the "Instructor access only" screen plus the same note; exam lists for students do not exist (me/exams is blocked by §2.4).

E. Authentication and security

TopicVerified behaviour and required frontend handling
Sign-inPOST /api/auth/login → TokenResponse. No cookies are used; tokens are only in the JSON body.
Access tokenJWT, HS256, issuer ExamProctoring.Api, audience ExamProctoring.Clients, lifetime 15 minutes (configurable), 30 s clock skew. Send Authorization: Bearer <token>. Use accessTokenExpiresAt to refresh slightly early. Claims (sub, role, security stamp) should not be parsed for authorization; use user from the token response.
Per-request account gateThe server checks on every request that the account exists, is Active and has the same security stamp. After a password change or admin action, old access tokens get 401 token_invalid.
RefreshPOST /api/auth/refresh with the refresh token → a new pair. Refresh tokens rotate; reusing an old one revokes the session (401 refresh_token_reused). Required: only one refresh at a time across the whole app (single-flight); retry the original request once after a successful refresh; sign out when refresh fails with 401/403.
LogoutPOST /api/auth/logout with the refresh token and the access token; 204. Clear local tokens even if the call fails. The access token remains technically valid until expiry (max 15 min).
Protected routesRequire a session; redirect to the change-password page while mustChangePassword; show "instructor access only" for other roles. Frontend checks are for UX only.
401 vs 403401 token_invalid: try one refresh, else sign in again. 403 password_change_required: change password. 403 without code: wrong role. Other 401/403 codes at login: show detail.
Token storageRequired for this project (as already implemented in the draft's src/auth/tokenStore.ts): the access token in memory only; the refresh token in sessionStorage, so a reload in the same tab keeps the session and closing the tab ends it. Never store either token in localStorage, URLs or logs, and never render untrusted HTML. Trade-off: any script running on the page can read sessionStorage, so XSS must be prevented (React escapes text; no dangerouslySetInnerHTML). Keeping the refresh token in memory only is stricter but loses the session on reload. HttpOnly cookies would be safer still, but the backend returns tokens only in JSON (no cookie option) and changing that is a backend change. The only value this app keeps in localStorage is the language preference (H.9).
Rate limitsPer IP: login 10/min, refresh 30/min, register 5/min → 429.
SecretsNo backend secret belongs in the frontend. Everything in VITE_* variables is public.
Security limitations to document in the frontend README: tokens readable by JavaScript (no HttpOnly cookies); no rate limits or body-size limits on exam/question endpoints (backend hardening planned for Phase 7); no CSRF concerns because no cookies are used.

F.2 CORS (verified in Program.cs and appsettings.json)

One policy allows only the origins in Cors:WebExamOrigins (any header, any method, no credentials). The list is empty, so a browser app on another origin is blocked. Two options:

  1. RECOMMENDED for development Vite dev-server proxy: forward /api to the backend URL of the profile in use (http://localhost:5168 for the http profile, https://localhost:7046 for https); the browser stays same-origin; no backend change.
  2. Direct calls: the backend team adds the frontend origin (e.g. http://localhost:5173 in development) to Cors:WebExamOrigins. This is a backend configuration change (decision D24) requiring approval; production needs the real origin.

F.3 HTTPS certificate

Only relevant with the https profile. The ASP.NET Core development certificate (dotnet dev-certs https --trust) is trusted by Windows browsers but not by Node.js, so a Vite proxy to https://localhost:7046 needs secure: false (the draft's default, local development only) or Node configured to trust the certificate. With the http profile and a proxy to http://localhost:5168 no certificate is involved.

F.5 API client RECOMMENDATION

export function localInputToApi(value: string): string {
  const d = new Date(value);                       // "2026-11-01T09:00" is parsed as LOCAL time
  const off = -d.getTimezoneOffset(), sign = off >= 0 ? '+' : '-', a = Math.abs(off);
  const p = (n: number) => String(n).padStart(2, '0');
  return `${d.getFullYear()}-${p(d.getMonth() + 1)}-${p(d.getDate())}T${p(d.getHours())}:${p(d.getMinutes())}:00` +
         `${sign}${p(Math.floor(a / 60))}:${p(a % 60)}`;
}

F.7 Access from another computer on the same network

localhost always means "this computer". A browser on another computer must use the LAN address of the machine that runs the servers (for example http://192.168.1.20:5173; find it with ipconfig). The API's launch profiles listen on localhost only and Cors:WebExamOrigins is empty.

  • RECOMMENDED Run the Vite dev server on the same machine as the API with npm run dev -- --host (listens on all interfaces). Other computers open http://<LAN-IP>:5173; the Vite proxy forwards /api to http://localhost:5168 on that machine. No backend binding or CORS change is needed; allow inbound TCP 5173 in Windows Firewall (private network profile only).
  • Alternative (backend change, needs the owner's approval; not done): make the API listen on the LAN (for example --urls http://0.0.0.0:5168 or a launch-profile change), allow inbound TCP 5168 in the firewall, and add the frontend's exact origin (for example http://192.168.1.21:5173) to Cors:WebExamOrigins; then set VITE_API_BASE_URL to http://<API-LAN-IP>:5168.
  • Plain HTTP on a LAN sends passwords and tokens unencrypted; acceptable only on a trusted development network.

K. Testing and acceptance checklist

Automated (mocked fetch) tests can run without the backend. Items marked [LIVE] need the backend running with a seeded admin, an instructor account, migrations applied and the dev proxy or CORS configured (F.6).

Authentication

  • Login success stores the session; instructor lands on the exam list.
  • Login 401 invalid_credentials / account_locked, 403 account_deactivated / temporary_password_expired, 429 show the right message and do not trigger a refresh.
  • mustChangePassword: true forces the change-password page; other pages redirect there; success returns to the exam list. [LIVE]
  • Expired access token → one refresh → original request retried; parallel requests trigger only one refresh.
  • Refresh rejected → signed out, redirected to login.
  • Logout calls the API and clears tokens even when the call fails.
  • Student/Admin account sees "instructor access only"; backend 403 confirmed. [LIVE]

Exams

  • List: default page 10; status filter in each value; page size change; next/previous; past-the-end page; empty state.
  • Create: valid exam → 201 → details page; start time sent with the browser offset; displayed correctly in local time. [LIVE for round trip]
  • Invalid submissions: empty title, 201-character title, 2001-character description, past start, duration 0 and 361 → messages; server 400 field errors mapped.
  • Edit: unchanged start time is sent unchanged; started or cancelled exam shows read-only explanation; 409 from server shown.
  • Delete Draft (confirm) → list; Delete not offered for Published/Cancelled.
  • Unknown or another instructor's exam id → not-found message. [LIVE]

Questions

  • MCQ create with 2+ options, one correct → appears at the end; Essay create sends no options.
  • Client blocks: no text, marks 0 / 10000 / 1.005, < 2 options, no correct option, repeated option text.
  • Server 400 for too many options shows the server message next to the options group. [LIVE]
  • Edit replaces options; MCQ→Essay removes options; Essay→MCQ requires valid options.
  • Delete renumbers positions; deleting the only question of a Published exam shows the 409 message. [LIVE]
  • Read-only panel after start / when cancelled.

Lifecycle

  • Publish with no questions → 409 "The exam has no questions." shown; exam reloaded.
  • Publish valid Draft → status Published, publishedAt shown; Unpublish → Draft, publishedAt cleared; publish again → new time. [LIVE]
  • Cancel requires confirmation; "Keep" sends nothing; confirm → Cancelled; all actions then hidden.
  • Buttons disabled after the start time; Delete of a past Draft still possible.

Student sign-up

  • Valid four-field form → 201 → success panel with the sign-in link; form and passwords cleared; no tokens stored; no automatic sign-in.
  • Client blocks empty fields, a 151-character name and mismatched passwords; server 400 messages appear on fullName, email, password (several policy messages) and confirmPassword.

Arabic / English

General
